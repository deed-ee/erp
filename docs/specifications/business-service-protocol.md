# Open Business Service Protocol and semantic model

Status: `1.0-draft`, language-neutral, not a compatibility guarantee. The [manifest schema](../../contracts/schemas/service-manifest-v1.json), [semantic descriptor schema](../../contracts/schemas/semantic-entity-v1.json) and [Master Data manifest](../../contracts/manifests/master-data-v1.json) are the executable reference fixtures. The Rust service implements the referenced HTTP operations but no registration API.

## Service manifests

The manifest identifies a service by a publisher-controlled dotted name and a numeric major/minor/patch version. `publisher` is descriptive, not proof of identity. `license` uses an SPDX expression or the pending sentinel `NOASSERTION`, which cannot be activated in a production registry. `platformCompatibility` lists supported protocol versions; `dependencies` maps service IDs to exact versions in this draft. `capabilities` are stable discovery IDs. A manifest links an OpenAPI document, entity descriptors, and service-relative liveness/readiness routes. Bundle-relative references resolve against the document containing the reference; runtime registration MUST use vetted, immutable bundles and must reject traversal, external reference fetching, and unresolved or invalid references. Relative `../` is valid only when the resolved file stays in the bundle root.

Planned registry flow: authenticate the publisher and deployment identity, bind the reviewed bundle digest to that identity, validate dependencies and referenced schemas, require operator approval of the deployment and its permission set, then activate the version. Reject by default, fail closed on incompatibility, and expose only activated manifests to consumers. Never route a service endpoint from an unverified manifest. Deactivation and rollback require dependency and migration checks. Manifest signatures, registration API, configuration schemas, emitted and consumed events, UI navigation, workflow actions, and a third-party conformance example are not delivered in this draft.

## Semantic entity descriptor

An entity links its representation schema and translation key, and maps names of operations to a `command` or `query`, an OpenAPI `operationId`, a required permission identifier and a UI localization key. The [Article descriptor](../../contracts/entities/article-v1.json) demonstrates `register` and `get` over the [Master Data API](../../contracts/openapi/master-data-v1.yaml). SKU uniqueness is enforced by the service's scoped database index, not by the descriptor. The demo bearer policy permits both operations; per-operation permission IDs are descriptive until the verified-identity slice. Descriptions provide no authority to access data. Future revisions can add relationships, domain lifecycle, declarative UI, and per-operation MCP or workflow bindings. State changes must still go through deterministic service commands.

Breaking payload or behavioral changes introduce a new major contract; compatible response additions must be optional for readers, and servers must not add mandatory request inputs to an existing version. Validate shipped fixtures and references in CI. The draft itself can change before the protocol is stabilized; keep producer and consumer examples in sync.

## Durable event convention (proposed)

The [envelope schema](../../contracts/schemas/event-envelope-v1.json) includes a UUID message ID, type equal to the NATS subject, payload schema major version, UTC timestamp, tenant and optional organization, source, typed actor, correlation, optional causation, optional W3C trace context, and a payload object. Subjects use `business.<domain>.<aggregate>.<past-tense-event>.v<major>` (e.g. `business.sales.order.confirmed.v1`); the suffix MUST match `schemaVersion`. Derived messages propagate correlation and identify the triggering message as causation. Define separate payload schemas per event and enforce subject/source, permissions, and scope at ingestion. The envelope is not a guarantee of delivery, ordering, or authenticity.
