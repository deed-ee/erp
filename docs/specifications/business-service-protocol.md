# Open Business Service Protocol and semantic model

Status: `1.0-draft`, language-neutral, not a compatibility guarantee. The [manifest schema](../../contracts/schemas/service-manifest-v1.json), [semantic descriptor schema](../../contracts/schemas/semantic-entity-v1.json) and [Master Data manifest](../../contracts/manifests/master-data-v1.json) are the executable reference fixtures. The Rust service implements the referenced HTTP operations but no registration API.

## Service manifests

The manifest identifies a service by a publisher-controlled dotted name and a numeric major/minor/patch version. `publisher` is descriptive, not proof of identity. `license` uses an SPDX expression or the pending sentinel `NOASSERTION`, which cannot be activated in a production registry. `platformCompatibility` lists supported protocol versions; `dependencies` maps service IDs to exact versions in this draft. `capabilities` are stable discovery IDs. A manifest links an OpenAPI document, entity descriptors, and service-relative liveness/readiness routes. Bundle-relative references resolve against the document containing the reference; runtime registration MUST use vetted, immutable bundles and must reject traversal, external reference fetching, and unresolved or invalid references. Relative `../` is valid only when the resolved file stays in the bundle root.

Planned registry flow: authenticate the publisher and deployment identity, bind the reviewed bundle digest to that identity, validate dependencies and referenced schemas, require operator approval of the deployment and its permission set, then activate the version. Reject by default, fail closed on incompatibility, and expose only activated manifests to consumers. Never route a service endpoint from an unverified manifest. Deactivation and rollback require dependency and migration checks. Optional `messaging` entries describe published/consumed messages, accepted commands and offered queries: layer, subject template, reviewed version bounds, relative contract reference, transport, delivery semantics, idempotency and permission requirements. They never grant access. Manifest signatures, registration API, UI navigation, workflow actions, and a third-party conformance example are not delivered in this draft.

## Semantic entity descriptor

An entity links its representation schema and translation key, and maps names of operations to a `command` or `query`, an OpenAPI `operationId`, a required permission identifier and a UI localization key. The [Article descriptor](../../contracts/entities/article-v1.json) demonstrates `register` and `get` over the [Master Data API](../../contracts/openapi/master-data-v1.yaml). SKU uniqueness is enforced by the service's scoped database index. The service enforces the two permission IDs against a trusted policy; metadata itself provides no authority. Future revisions can add relationships, domain lifecycle, declarative UI, and per-operation MCP or workflow bindings. State changes must still go through deterministic service commands.

An optional `discovery` annotation on a query identifies its single typed OpenAPI parameter, localized phrase prefixes, and the OpenAPI operation that checks discoverability under the caller's current scope. The Article examples point at `HEAD` on the exact SKU and exact name lookups. Those checks read no records, confer no execution rights, and do not bypass the `GET` authorization. The [command prototype](command-interface.md) imports the reviewed manifest and descriptor at build time; it neither loads arbitrary endpoints nor implements runtime registration. No annotation enables a command or an MCP tool.

Breaking payload or behavioral changes introduce a new major contract; compatible response additions must be optional for readers, and servers must not add mandatory request inputs to an existing version. Validate shipped fixtures and references in CI. The draft itself can change before the protocol is stabilized; keep producer and consumer examples in sync.

For INT-002, the [Article v1 reader fixture](../../tests/contracts/fixtures/article-reader-v1.json) freezes example data and required HTTP operations from its recorded source commit. The [contract check](../../tests/contracts/check.py) verifies the historic request and response still validate, and that both operations and their guaranteed response fields remain. This is a regression check for the Article draft, not a full schema-diff tool or a stability promise. Do not update the historical fixture to pass an incompatible change: a breaking Article v1-to-v2 migration must name both versions and document how clients move to the new major contract.

## Messaging transport

Use the [NATS wire specification](nats-messaging.md) for versioned application messaging. This transport protocol version is independent of the manifest format's `1.0-draft`. The original [local event schema](../../contracts/schemas/event-envelope-v1.json) remains for historical outbox entries and pre-cutover fixtures; the old unscoped subject is not an application publish route for new integrations.
