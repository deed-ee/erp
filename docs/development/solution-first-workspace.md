# Solution-First Workspace

**Solution First. Function First. Data Second.** Start with the user's decision, surface the supporting facts and a next permitted step, then provide tables and forms for comparison or detail. One capability may have several entry points, not several business implementations. Essential operations must remain usable without a provider or natural-language input. See the [GitHub milestone](https://github.com/erp4us-org/erp4us/milestone/6), [UI-003–UI-010](../requirements/ui-foundation.md), [ADR 0004](../adr/0004-ui-foundation.md) (proposed) and [agent guidance](../../AGENTS.md#start-with-the-users-decision).

## Run the first slice

Start the loopback [Master Data quickstart](../../README.md#run-the-first-slice) and [Angular workspace](../../README.md#try-the-local-angular-workspace) with synthetic data. Load a short-lived token via **Preferences → Local demo access**; register `BRACKET-1` (or choose a fresh SKU) in Products. Open global search using Ctrl+K or Cmd+K, choose the suggested query, complete it with the SKU, and open the returned article. Switch language in Preferences and repeat with `Zeige mir den Artikel mit SKU BRACKET-1`. The Products screen also offers an exact SKU form leading to the same record. Register two different SKUs using the exact same name and query `Find article named "Steel bracket"` (for a label you registered). Choose a SKU from the result; same-named articles in other scopes are never candidates. A non-existent SKU or name found only out of scope yields no authorized match; a missing grant or service failure is not an empty result.

The shell keeps the existing trusted navigation metadata and component patterns. It shows the local environment, actual UI package version and known scope; it does not guess system health. German/English, theme and density preferences are local display settings; the authorization token, query and result are not stored in them. The landing page links to a real available task. The task service is explicitly unavailable; the screenshots do not imply that stock, KPIs or tasks exist.

### Proposed build-blocker review

The evidence must be anchored in a selected authorized order line and its pinned product/BOM revision. If only product and requested quantity are known and several orders fit, ask the user which order; a gross requirements preview can describe structure but cannot establish an allocation. If the line is service-only, show that material analysis does not apply rather than a zero-shortage readiness claim.

For the synthetic NovaMotion example, start with **12 end plates missing** and the path `NM-1000/A → NM-1100/A → end plates`, supported by 20 required and 8 held in the original plan. Project owner-supplied aggregate quantities once per allocation identity; show multiple structural paths as references, not duplicate stock or additive shortages. An expected delivery does not increase held stock. After six are physically posted and allocated, the current read must show 14 held and 6 missing, while the historical plan remains unchanged. Replays, stale projections, denied Procurement data, missing revisions and restarted services must not invent receipts or prove readiness. Expose exact quantities and their sources and a keyboard-accessible textual drill-down. A command and the direct product/order route must reach the same explanation with the same grants. This is acceptance design, not a fixture answer or a change to the Preview.
