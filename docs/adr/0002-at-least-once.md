# ADR 0002: Local transactions and at-least-once messages

**Status:** accepted; Article registration is exercised across two local services.

Use JetStream with a MongoDB transactional outbox and idempotent subscribers. Persist an inbox marker and the resulting state change in the consumer's transaction; do not mark a message consumed on broker receipt. An outbox relay crash after publish but before local completion may republish; stable IDs and consumer-side deduplication are required. Later subscribers define a replay policy and distinguish event time from processing order. Alternatives rejected: direct publish after business writes (loss window) and distributed transactions (coupled failures).

Master Data commits the article and the [`ArticleRegistered` envelope](../../contracts/schemas/article-registered-v1.json) in a single transaction on the Compose replica set. The stored UUID is the stable message ID and also starts the correlation chain. The payload identifies the article and revision without including the SKU or name. Existing articles are not backfilled.

The optional local delivery stack uses one Master Data relay and a separate Article Receipts consumer with its own database and credentials. The relay records `publishedAt` only after a JetStream acknowledgement. The consumer atomically upserts a single document keyed by message ID: the document is both the receipt and inbox marker, so a replay cannot create a second receipt. Invalid events are recorded by stream sequence without retaining their payload in the database, then terminated. The original message stays in JetStream for operator inspection.

This slice handles initial registration only (revision 1). The relay scans by creation timestamp and MongoDB key, but that is not a business ordering guarantee; receipts can arrive out of order (including after replay) and do not depend on other events. The stream is size-limited and rejects new writes when full instead of evicting old messages. The relay leaves those writes pending and retries; there is no automated stream retention, pressure alert or coordinated broker/database recovery. This is not a production deployment.

The consumer attempts to persist a receipt on at most the first four deliveries of a stream message. Failed attempts request redelivery after 1, 2 and 4 seconds. At exhaustion, it records the stream sequence, message and correlation IDs, scope and delivery count in quarantine without copying the payload. It terminates delivery only after that record is durable. If quarantine is unavailable, it retries quarantine after 10 seconds instead of dropping the message; while that message is pending, the single-in-flight consumer may stop making progress. JetStream's delivery counter survives worker restarts and includes deliveries interrupted before a database write.

For a successful registration Master Data generates a new W3C `traceparent`, logs it and returns it in the HTTP response. It does not trust a client-supplied value. The outbox payload carries it as envelope metadata; the relay also sets the NATS header. The receipt and retry-exhaustion record retain the same value. Older events without trace context remain readable. This is correlation, not span collection or an OpenTelemetry exporter.

After correcting a transient persistence problem, a trusted local operator can replay one retry-exhausted stream sequence at a time. The command checks the stored event against the quarantine record's message, scope and correlation IDs. It republishes the unchanged envelope with a separate, deterministic broker deduplication key and records the request and broker-confirmed replay sequence in quarantine. This does not confirm consumer completion; inspect the receipt with the original message ID. Invalid envelopes cannot be replayed through this command. A confirmed quarantine entry cannot be replayed again; if a replay exhausts retries, it has its own sequence. If the broker accepts a replay but recording the acknowledgement fails, rerunning can republish outside the broker's deduplication window. The receipt's original message ID still prevents duplicate effects. Do not run overlapping replay commands; Docker access is the local operator boundary.
