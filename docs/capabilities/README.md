# Who owns a fact?

The [map](map.yaml) is a two-level hierarchy: domain → named capability (`DOMAIN.01`). A node identifies a purpose, actor, concept relationship, lifecycle actions, example event, invariant, report, dependencies and open question. Events here are candidate business vocabulary, not published messages. Domain dependencies can be reciprocal; requirement prerequisites must form a DAG. The [architecture baseline](../architecture/baseline.md) takes precedence. Owners outside its established boundaries are analysis candidates, not approved services.

**Read each node with these common constraints:** the listed actor is a participant, not an automatic grant. The fact owner authorizes actions within tenant and permitted organizations. A shared definition, local override or cross-entity report requires explicit policy. Preserve the effective definition or snapshot for historical decisions, record corrections rather than destructive edits, localize labels independently of identity and retain original units/currency. Configure optional roles and capabilities per operating model. Specialists in a one-person firm may coincide; a regulated approval may still require separation. Integrate through published commands and versioned events. Never treat a displayed relationship or a report as the source of a posting.

For domain-specific variants, find the node's ID in [reference companies](../scenarios/companies.yaml), then inspect its [requirement file](../requirements/catalog/). A missing scenario is a discovery gap. Authority disputes: Inventory owns quantities and holds, Quality owns disposition, Procurement owns the PO, Sales owns the customer promise. Workflow shows their progress; Analytics can rebuild views but cannot correct those source facts. Unit definitions do not own contextual transaction readings; Organizations does not own warehouse balances.
