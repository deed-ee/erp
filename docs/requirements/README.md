# Public business requirements catalog

IDs are permanent, including when a requirement is deferred or replaced. Dependencies refer to concepts required by the target capability, not a requirement to deliver the entire dependency before starting a slice. Owners coordinate the requirement; other domains retain their own invariants. Milestones follow the [roadmap](../../ROADMAP.md); the [business domain model](../architecture/business-domain.md) describes the target boundaries.

**Classes:** Commitment (architectural constraint), MVP (bounded release evidence), Planned (future capability), Proposal (unaccepted community RFC), Experimental (time-boxed hypothesis, not a compatibility promise). **Status** is separate: not started, partial, implemented, or deferred. A documented commitment is not a delivered feature. Scenario links are planned checks unless marked executable.

## Traceability and contributions

Foundation example: **BD-018** → [Article domain](../../services/master-data/src/domain.rs) → [OpenAPI](../../contracts/openapi/master-data-v1.yaml) and [semantic descriptor](../../contracts/entities/article-v1.json) → [HTTP](../../services/master-data/src/http.rs) and [MongoDB store](../../services/master-data/src/store.rs) → executable checks above.

For new work, use the [public RFC process](../../GOVERNANCE.md#rfc-process) and cite requirement/scenario IDs in design and PRs. When a contract or implementation lands, add links here (or from a linked evidence page) to the specific model, contracts, code and tests. Keep planned checks distinct from executable evidence. Do not mark the broader commitment implemented because one slice passes.
